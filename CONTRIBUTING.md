# Contributing to rules_ocx

Thanks for helping out! Ground rules:

## Workflow

- Conventional Commits (`feat:`, `fix:`, `docs:`, `test:`, `ci:`, `chore:`).
  The changelog is generated by git-cliff from commit messages.
- Branch from `main`, open a PR. Never push to `main` directly.
- `task verify` must pass locally before requesting review. It runs the
  linters plus `bazel test //...` and the example workspaces.

## Design invariants

- **Never re-implement OCX internals in Starlark.** No OCI protocol, no
  registry auth, no index/store layout knowledge. Everything goes through the
  pinned `ocx` CLI; if the CLI is missing a capability, file an issue against
  [ocx-sh/ocx](https://github.com/ocx-sh/ocx) instead.
- The pinned ocx version (`ocx/private/versions.bzl`) and the vendored
  manifest (`dist/dist.json`) are bumped together, deliberately.
- The extension reads only `module_ctx.os`, the tags, the tag's `ocx.lock` and
  the `OCX_INSTALL_*` variables, and runs `ocx vendor --manifest-only` only to
  compute facts that miss; every other host interaction lives in repository
  rules (`AGENTS.md`, invariant 3).
- `ocx vendor` is the only ocx command rules_ocx runs and `manifest.json` the
  only ocx document it reads; `task guard:check` enforces both.

## Toolchain

The dev toolchain is provisioned by OCX itself (dogfooding): ocx's prompt
hook (`ocx self setup --hook` once, then `ocx shell allow` in this checkout —
the hook stays inert until the project has a consent stamp) gives you bazelisk, actionlint, git-cliff, and friends from the committed
`ocx.toml`/`ocx.lock`; or prefix a command with `ocx exec --`.
